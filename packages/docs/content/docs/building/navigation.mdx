An app is a tree of pages. Some pages hold stacks of pages of their own: a share sheet with its own steps, or tabs with a stack per tab. A `<Navigator>` draws one stack with Flutter's Navigator. The stacks themselves are data in JS, so links and restore can rebuild the whole tree before anything draws.

## File routes

Pages live in `src/app/`. Each file is a page at the address its path names.

```
src/
  index.tsx            render(() => <FileRoutes />)
  app.tsx              the app: draws the app's own stack
  app/
    index.tsx          /
    settings.tsx       /settings
    users/
      index.tsx        /users
      [id].tsx         /users/:id
    share.tsx          /share: holds share/
    share/
      index.tsx        /share, the first page inside it
      contact.tsx      /share/contact
    tabs.tsx           /tabs: holds tabs/, a stack per tab
    tabs/
      index.tsx        /tabs, the feed tab
      profile.tsx      /tabs/profile, the profile tab
      post/[id].tsx    /tabs/post/:id
      _components/     not pages
```

- **`index`** is its folder's own page. **`[id]`** is a param. **`(group)`** folders stay out of the address. Files and folders starting with **`_`** aren't pages, so helpers and components can sit next to the pages that use them.
- **`x.tsx` holds `x/`** when `x/index.tsx` exists. The two share the address `/x`: `x.tsx` is the UI around the folder's stacks, `x/index.tsx` is the first page in them. Without `x/index.tsx`, the pages in `x/` open where `x` opens.
- **`src/app.tsx` holds `src/app/`.** It draws the app's own stack, usually inside a design's app root.
- **`name@x.tsx`** opens in the stacks `x.tsx` holds instead of its folder's. `@app` is the app's own stack: `tabs/settings@app.tsx` sits with the tabs in the file tree but covers them when it opens. Two holders with the same name are a build error.

```tsx title="src/index.tsx"
import { render } from "solid-fuse";
import { FileRoutes } from "#fuse/routes";

render(() => <FileRoutes />);
```

```tsx title="src/app.tsx"
import { MaterialApp } from "@solid-fuse/material";
import { Navigator } from "solid-fuse";

export default function App() {
  return (
    <MaterialApp>
      <Navigator />
    </MaterialApp>
  );
}
```

A page's default export is its component; its props are its params. It can also export `page`, how it comes in, and `parse`, which turns the params an address brings into what the page takes. They are always strings, from the path and the query; what `parse` returns is merged over them:

```tsx title="src/app/users/[id].tsx"
import { useNav } from "solid-fuse";

export const parse = (p: { id: string }) => ({ id: Number(p.id) });

export default function User(props: { id: number }) {
  const nav = useNav();
  return <Button onPress={() => nav.push("/share")}>Share</Button>;
}
```

Only addresses go through `parse`: `nav.push(routes["/users/[id]"], { id: 42 })` passes the number as it is, and restore brings back what the page had. A schema works too: `export const parse = (p) => schema.parse(p)`. When `parse` throws, the address isn't this page's: the next route that matches it gets a go, and with none left the address opens nothing.

Addresses are typed: `nav.push("/userz")` is an error. `fuse dev` writes `fuse/routes.tsx` again when a file in `src/app/` changes; don't edit it. It also exports `routes`, every page by file: `routes["/users/[id]"]`.

## Pushing

`nav.push(address)` opens a page where its file says:

1. on the stack whose first page it is,
2. else on the stack whose first page's address starts its own (`/tabs/profile/edit` on the profile tab),
3. else on the stack in front.

That's all inside the page holding its folder. If that page isn't open, it opens first; if it's covered by another page, the new page goes on top of the cover, so you always see it. If it's open but hasn't drawn its stacks yet (say they're behind a login), the push waits until they draw.

```tsx
const nav = useNav();
nav.push("/users/42");
nav.push(() => <Detail />); // a page without a file: on the stack you're on
const fruit = await nav.push<string>(() => <Picker />); // what it gives to pop(result), or null
```

| | |
|---|---|
| `nav.push(address \| route, params?, options?)` | Open a page where its file says. `options.page` overrides how it comes in. |
| `nav.push(() => <X />)` / `nav.push(page({...}))` | Push a page without a file on the stack you're on. |
| `nav.pop(result?)` | Pop the top of your stack. On its first page, this closes the page holding it. |
| `nav.replace(...)` | Swap the page on top of your stack. |
| `nav.go(address)` | Open an address as a link does (below). |
| `nav.stack` | The stack this page is on. |
| `nav.app` | The app's own stack. |

A stack gives `index` (its first page's address), `pages()` and `top()` (reactive), `push` (onto this stack, whatever the file says), `pop(result?)`, and `set(pages)`, which replaces every page above the first; `set([])` goes back to it.

## Holding stacks

A page that holds stacks draws them with `<Navigator>`. UI around it stays put while its pages change.

```tsx title="src/app/share.tsx"
import { Navigator, Text, View } from "solid-fuse";

export default function Share() {
  return (
    <View layout={{ direction: "vertical" }}>
      <Text fontSize={20}>Share</Text>
      <View flex={1}>
        <Navigator />
      </View>
    </View>
  );
}
```

`<Navigator />` starts at the page's own address: `share/index.tsx`. `<Navigator index="/share/contact" />` starts somewhere else. A page can draw as many as it likes, each a stack of its own, all kept alive. `usePage()` is the page's own place in the tree:

| | |
|---|---|
| `page.stacks()` | The indexes of the stacks it holds, in the order they drew. |
| `page.active()` | The stack in front: the one that takes the back button and gets pushes that fit no other. When it stops drawing, one drawn in its place comes to the front (the app's stack after sign-in). |
| `page.show(index)` | Bring a stack to the front. Showing the one in front again pops it to its first page. |
| `page.stack(index?)` | A stack it holds; the first without an index. |

## Tabs

`<Tabs>` shows the stack in front and keeps the rest alive. Hidden ones don't tick or take back, and back on another tab's first page goes to the first tab. Write the bar yourself.

```tsx title="src/app/tabs.tsx"
import { For } from "solid-js";
import { Navigator, Tabs, usePage } from "solid-fuse";
import { NavigationBar, NavigationDestination, Icons } from "@solid-fuse/material";

const tabs = ["/tabs", "/tabs/profile"];

export default function Main() {
  const page = usePage();
  return (
    <View layout={{ direction: "vertical" }}>
      <View flex={1}>
        <Tabs>
          <For each={tabs}>{(index) => <Navigator index={index} />}</For>
        </Tabs>
      </View>
      <NavigationBar selected={tabs.indexOf(page.active()!)} onSelect={(i) => page.show(tabs[i]!)}>
        <NavigationDestination icon={Icons.home} label="Feed" />
        <NavigationDestination icon={Icons.person} label="Profile" />
      </NavigationBar>
    </View>
  );
}
```

`/tabs/post/1` from the profile tab opens on the profile tab, the one in front. `/tabs/profile/edit` from the feed opens on the profile tab and shows it. `Tabs` is a small helper over `usePage()`: write your own for a pager or a rail.

## Links

`nav.go("/tabs/post/1")` opens an address as a link does. The stacks on its way go back to their first page, the pages holding it open outermost first, and pages at the addresses in between open below it, so back goes up: `/users/42` gives `[home, users, user 42]`. Query params become params too: `/search?q=solid`. The other way round, `addressOf(route, params)` (and a page's `address`) puts params that aren't in the path in the query when they are strings, numbers or booleans, so an address always opens the same page.

A link the OS opens goes the same way, at launch and while the app runs. A link into stacks that haven't drawn yet waits for them; only the latest one waits. Your app has to ask the OS for its links first: an intent filter on Android, associated domains or a URL scheme on iOS. See Flutter's deep linking guide; the rest is solid-fuse's.

## Back

The Android back button pops the stack in front, from the innermost page that holds stacks outwards. On its first page, it pops the stack around it. iOS swipe-back and the back gesture work per Navigator, as in Flutter.

## Restore

When the OS kills an app in the background and starts it again, the whole tree comes back: every change saves the pages and their params, and the app puts them back before anything draws. Pages without a file aren't saved, nor anything above them. This works where Flutter's state restoration does: Android, and iOS once the runner gives the Flutter view controller a restoration ID.

## Routes without files

Each file is a `route()`, and anything a file can say, `route()` can say. Use it for an app without file routes, or a package that brings its own pages.

```tsx
import { Navigator, route } from "solid-fuse";

const Home = route({ path: "/", component: HomePage });
const Share = route({ path: "/share", page: sheet, component: ShareSheet });
route({ path: "/share", in: Share, component: ShareHome }); // share/index.tsx
const Contact = route({ path: "/share/contact", in: Share, component: ContactPicker });
const Picker = route({ component: PickerPage }).returns<string>();

render(() => <App><Navigator /></App>);
```

| Option | |
|---|---|
| `component` | The page. Gets the params as props. |
| `path` | Its address, `"/users/:id"`. Without one, it can be pushed but not linked to or restored. |
| `in` | The page whose stacks it opens in. Without it, the app's own stack. |
| `page` | How it comes in: `(child) => materialPage({ child, fullscreenDialog: true })`. Default: the app's page type. |
| `parse` | Turns the params an address brings (strings) into what the component takes. Its result is merged over them; a throw means the address isn't this page's. |

`.returns<T>()` types what `pop(result)` gives back. `addressOf(User, { id: 42 })` is `"/users/42"`. Declare your addresses to type `push` and `go`: `declare module "solid-fuse" { interface Register { address: "/" | \`/users/${string}\` } }`.

## Pages are configs

How a page comes in is a config, `{ type, child, props }`. Core's `page({...})` makes one; the design packages add `materialPage` and `cupertinoPage`, and heroine `heroinePage`. A page without a `page` export is one of the app's type: `page` under `<App>`, `materialPage` under `<MaterialApp>`, `cupertinoPage` under `<CupertinoApp>`.

```tsx title="src/app/settings.tsx"
import { materialPage } from "@solid-fuse/material";

export const page = (child) => materialPage({ child, fullscreenDialog: true });
```

### page props

Core's page has no design: the content brings its own background.

| Prop | Type | Default | Description |
|---|---|---|---|
| `child` | `() => JSX.Element` | required | Page contents |
| `name` | `string` | — | Flutter's `Page.name` |
| `transition` | `"slide" \| "fade" \| "none"` or a function | `"slide"` | How the page comes in (see below) |
| `duration` | `number` | `300` | Transition length in ms |
| `reverseDuration` | `number` | `duration` | Length going out |
| `barrierColor` | `Color` | — | Covers the page below (with `opaque: false`) |
| `barrierDismissible` | `boolean` | `false` | A tap on the barrier pops the page |
| `opaque` | `boolean` | `true` | False lets the page below show through |
| `fullscreenDialog` | `boolean` | `false` | |
| `maintainState` | `boolean` | `true` | Keep state alive when not the top page |

### Transitions in JS

`transition` can be your own: wrap the page in Flutter's transition widgets, driven by the route's animations. It runs once per route; the widgets follow the animations in Dart, so nothing runs in JS per frame.

```tsx
import { page as pageOf } from "solid-fuse";
import { FadeTransition, ScaleTransition } from "#fuse/flutter";

export const page = (child) =>
  pageOf({
    child,
    transition: (content, { animation }) => (
      <FadeTransition opacity={animation}>
        <ScaleTransition scale={animation}>{content}</ScaleTransition>
      </FadeTransition>
    ),
  });
```

`animation` runs as the page comes and goes; `secondaryAnimation` as the next page covers it. Curves come from `createCurvedAnimation({ parent: animation, curve: Curves.easeOut })`. `heroinePage` takes a `transition` too.

### materialPage props (`@solid-fuse/material`)

| Prop | Type | Default | Description |
|---|---|---|---|
| `child` | `() => JSX.Element` | required | Page contents |
| `name` | `string` | — | Flutter's `Page.name` |
| `fullscreenDialog` | `boolean` | `false` | Slides up instead of sideways, shows close button |
| `maintainState` | `boolean` | `true` | Keep state alive when not the top page |

`cupertinoPage` (`@solid-fuse/cupertino`) takes the same, plus `title`, which the next page's back button shows.

## Heroes and observers

Flutter's `Hero` flies between pages of a `<Navigator>`. `observers` takes Flutter's `NavigatorObserver`s, which see every push and pop. They are generated handles: `createNavigatorObserver()` and `createHeroController()` from `#fuse/flutter`, or a package's own, such as heroine's controller ([Animation](/docs/building/animation#hero-transitions-on-springs)).

```tsx
const heroine = createHeroineController();

<Navigator observers={[heroine]} />
```
