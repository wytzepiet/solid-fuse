Every Fuse widget has two parts: a **JS wrapper component** (what consumers import and write in JSX) and a **Dart widget builder** (how it renders). This page walks through creating a custom widget from scratch.

> Before building from scratch, check [pub.dev](https://pub.dev) — the Dart side is just Flutter, so an existing package (charts, maps, video, pickers) can be wrapped instead of reinvented. The mechanics are identical to this page; see [Using pub.dev packages](/docs/extending/using-packages).

## The two-file pattern

Let's build a `Badge` widget that renders a Flutter `Chip`.

### Step 1: Write the JS wrapper

```tsx title="src/badge.tsx"
import type { Color } from "#fuse/flutter";
import type { LayoutInput } from "solid-fuse";

export interface BadgeProps {
  label: string;
  color?: Color;
  children?: any;
  layout?: LayoutInput;
}

export function Badge(props: BadgeProps) {
  return <badge {...props} />;
}
```

The lowercase `<badge>` is the wire format — the Solid universal renderer creates a node with `type: "badge"` that Dart will look up. Consumers never see it; they import `Badge` and write `<Badge label="New" />`.

Attributes written directly on the lowercase tag work like on any JSX element, so a wrapper can pin or default props instead of spreading everything:

```tsx
export function Badge(props: BadgeProps) {
  return <badge color="#2563EB" label={props.label} onTap={() => console.log("tapped")} />;
}
```

Literal values and handlers (`color`, `onTap`) are sent together with the node's creation; expressions that read props or signals (`label`) update whenever they change.

> You don't need to declare `<badge>` in a `.d.ts` file — `solid-fuse` defines the JSX namespace as an open `[name: string]: any` catch-all so any lowercase tag works.

### Step 2: Write the Dart widget

```dart title="dart/lib/src/widgets/badge.dart"
import 'package:material_ui/material_ui.dart';
import 'package:solid_fuse/solid_fuse.dart';

class FuseBadge extends StatelessWidget {
  const FuseBadge(this.node);

  final FuseNode node;

  @override
  Widget build(BuildContext context) {
    final label = node.string('label') ?? '';
    final color = node.value<Color>('color') ?? Colors.blue;

    return Chip(
      label: Text(label),
      backgroundColor: color,
      side: BorderSide.none,
    );
  }
}
```

### Step 3: Register

```dart
runtime.registerWidget('badge', FuseBadge.new);
```

Now consumers can use it:

```tsx
import { Badge } from "./badge";

<Badge label="New" color="#16A34A" />
```

## Why wrappers?

Wrapper components are the seam between user code and the renderer. Once you own that seam you can:

- Provide typed props so consumers get autocomplete and type errors
- Add default props, theme injection, dev-mode warnings, or perf marks later — in one place, without renaming every callsite
- Tree-shake unused widgets out of production bundles

Adding JS behavior to a widget no longer means switching from `<widget>` to `<MyWidget>` — the wrapper is already there.

The built-in wrappers cost nothing at runtime: `fuse dev` and `fuse build` compile `<View>`, `<Text>` and the others as the element they render. An app can get the same for a package's wrappers that do nothing but forward their props (`props => <badge {...props} />`) by naming them in `fuse.config.ts`:

```ts title="fuse.config.ts"
export default defineConfig({
  compile: { intrinsics: { "my-badges": { Badge: "badge" } } },
});
```

Leave a wrapper out of that list as soon as it does anything more than forward props; it then runs as the ordinary component it is.

A wrapper that does run adds little. When `<Badge label="New" color={tone()} />` reaches `<badge {...props} />`, the renderer looks at how each prop was written: a literal (`label`) is sent once with the node's creation and never tracked, and only expressions (`color`) share a reactive binding. Props that come from a store or from `merge()` are tracked as a whole, since their keys can change.

## FuseNode prop accessors

`FuseNode` extends `FuseMap`, which provides typed accessors for reading props. All return nullable — if the prop wasn't set in JSX, you get `null`.

| Accessor | Returns | What it parses |
|---|---|---|
| `string(key)` | `String?` | String values |
| `double(key)` | `double?` | Numbers |
| `int(key)` | `int?` | Integers |
| `bool(key)` | `bool?` | Booleans |
| `map(key)` | `FuseMap?` | Nested objects (also has typed accessors) |
| `list<T>(key)` | `List<T>?` | Arrays |
| `enumOf(key, values)` | `T?` | An enum by name: `node.enumOf('align', TextAlign.values)` |
| `clipBehavior(key)` | `Clip` | `"hardEdge"`, `"antiAlias"`, `"none"` (defaults to `Clip.none`) |
| `value<T>(key)` | `T?` | A Flutter value: `node.value<Color>('color')`, `node.value<EdgeInsetsGeometry>('padding')` (on `FuseNode`) |
| `values<T>(key)` | `List<T>?` | A list of them: `node.values<Shadow>('shadows')` |

Nested objects return `FuseMap`, which has the same accessors — so you can do `node.map('config')?.string('mode')`.

`value<T>` decodes a value the way generated widgets do, short forms included, so the prop's TypeScript type is the generated one (`Color` from `#fuse/flutter`). It works for every class a `lib/fuse.dart` names with `show`; solid-fuse's names `Color`, `EdgeInsetsGeometry`, `AlignmentGeometry`, `BoxDecoration`, `TextStyle`, `FontWeight`, `Shadow` and `TextDecoration`. For another type, add it to your own barrel (`export 'package:flutter/widgets.dart' show BoxConstraints;`).

## The layout + layoutChildren mechanic

> If you add `layout?: LayoutInput` to your wrapper props and use `node.layoutChildren` in your Dart widget, **layout just works**. Users of your widget can pass `layout={{ direction: "horizontal", gap: 8 }}` and children will arrange automatically — you don't write any layout code.

This is how every built-in element handles children. Here's a wrapper that supports it:

```tsx title="JS wrapper"
import type { LayoutInput } from "solid-fuse";

export interface MyCardProps {
  children?: any;
  layout?: LayoutInput;
}

export function MyCard(props: MyCardProps) {
  return <myCard {...props} />;
}
```

```dart title="Dart widget"
class FuseMyCard extends StatelessWidget {
  const FuseMyCard(this.node);
  final FuseNode node;

  @override
  Widget build(BuildContext context) {
    return Card(
      child: Padding(
        padding: const EdgeInsets.all(16),
        child: node.layoutChildren,  // ← reads the layout prop automatically
      ),
    );
  }
}
```

Now consumers can do:

```tsx
<MyCard layout={{ gap: 8 }}>
  <Text>Title</Text>
  <Text>Subtitle</Text>
</MyCard>
```

### How layoutChildren works

- Reads the `layout` prop from the node
- Wraps the children in a Flutter `Flex` (a column unless `layout` says otherwise) with the specified gap, alignment, and justification
- If there's only one child, no `layout` config and no child with a `flex` share: returns the child directly (no wrapper)
- Children that draw elsewhere (`<Modal>`) are mounted beside the layout, never in it
- A child's `flex` share is handled by the child itself: every element wraps itself in an `Expanded` when it has one, so your widget does nothing for it

### childWidgets vs layoutChildren

- **`node.layoutChildren`** — reads the `layout` prop and applies layout. Use this for anything that should support user-configured layout. This is the recommended default.
- **`node.children`** — the child nodes themselves. Empty text nodes are left out of all three: Solid keeps one as a placeholder where a dynamic child currently renders nothing (a hidden `<Show>`), and like an empty text node in the DOM it takes no space.
- **`node.childWidgets`** — raw list of child widgets, no layout applied. Use this when you're passing children to a Flutter widget that manages its own layout (like `Navigator` or `Stack`).

## Event callbacks

To support event callbacks from Dart to JS, use `node.callback()`:

```dart
// Returns a callback if the prop was set in JSX, null if not
final onTap = node.callback('onTap');

// Safe to use directly — null means "no handler"
GestureDetector(
  onTap: onTap,
  child: node.layoutChildren,
)
```

Under the hood: when you write `onTap={() => doSomething()}` in JSX, the actual function is stored in a JS-side handler map. The Dart prop is just `true` — a marker that a handler exists. When Dart calls the callback, it sends a message back to JS via the bridge, which looks up and executes the real function.

To send data back with the callback:

```dart
node.callback('onChange')?.call(newValue);
```

## StatefulWidget

Use `StatefulWidget` when your widget needs persistent Dart-side state (animations, text editing, controllers). Flutter preserves `State` across rebuilds because each `FuseNodeWidget` uses `ValueKey(node.id)` — so your state survives prop changes and tree updates.

```dart
class FuseTextInput extends StatefulWidget {
  const FuseTextInput(this.node);
  final FuseNode node;

  @override
  State<FuseTextInput> createState() => _FuseTextInputState();
}

class _FuseTextInputState extends State<FuseTextInput> {
  late final _controller = TextEditingController();

  @override
  void dispose() {
    _controller.dispose();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    return TextField(
      controller: _controller,
      onChanged: (value) => widget.node.callback('onChange')?.call(value),
    );
  }
}
```

## Where should your widget live?

| Location | When to use | How to register |
|---|---|---|
| **In your app** | Domain-specific, uses app-level deps | `runtime.registerWidget(...)` after packages |
| **In a Fuse package** | Reusable across apps, has its own deps | Via `register()` function + `fuse link` |
| **In solid-fuse** | Core Flutter primitives any app needs | PR to the framework |

To wrap an existing Flutter package instead of building from scratch, see [Using pub.dev packages](/docs/extending/using-packages). For creating a reusable package, see [Packaging](/docs/extending/packaging).
