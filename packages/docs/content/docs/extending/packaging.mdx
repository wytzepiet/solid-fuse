## fuse.config.ts

Every Fuse project — whether it's a reusable package or a consumer app — uses a `fuse.config.ts` file.

### Library package config

```ts title="fuse.config.ts"
import { defineConfig } from "solid-fuse/config";

export default defineConfig({
  library: true,
  register: "register",   // Name of the Dart top-level registration function
});
```

`library: true` opts the package into `fuse build`'s library mode (ESM output with `solid-js` and `@solidjs/universal` externalised). `register` names a top-level Dart function that `fuse link` will call, for the package's hand-written widgets, handles and pages. A package whose Dart is all [generated](/docs/extending/generating) from its `dart/lib/fuse.dart` leaves it out. The Dart side exports it like this:

```dart title="dart/lib/src/register.dart"
import 'package:solid_fuse/solid_fuse.dart';

void register(FuseRuntime runtime) {
  runtime.registerWidget('myWidget', FuseMyWidget.new);
  runtime.registerHandle('myController', FuseMyController.new);
  runtime.registerHandle('myPage', FuseMyPage.new);
}
```

The `registerHandle` call covers both imperative handles (extending `FuseHandle<T>`) and custom navigator pages (extending `FusePageHandle`).

### App config

Consumer apps can override Vite and Solid plugin settings:

```ts title="fuse.config.ts"
import { defineConfig } from "solid-fuse/config";

export default defineConfig({
  vite: {
    resolve: {
      alias: { "~": "./src" },
    },
  },
});
```

Fuse auto-configures the Solid plugin with `generate: "universal"` and `moduleName: "solid-fuse"`, and sets up Vite with an es2020 target and IIFE build output. You only override what you need.

### Config options

| Option | Type | Default | Description |
|---|---|---|---|
| `library` | `boolean` | `false` | Mark this package as a Fuse library. Enables `fuse build`'s library mode (ESM with externalised peers). |
| `register` | `string` | none | Name of the Dart top-level registration function; leave out when the package has no hand-written Dart |
| `dart` | `string` | `"dart"` | Path to the Dart/Flutter package directory |
| `platforms` | `string[]` | `[]` | The app's platforms (`android`, `ios`, `macos`, `linux`, `windows`). `fuse dev` and `fuse build` add a missing one's folder (`dart/android/`...) with `flutter create`. Commit it: then it's yours, and fuse doesn't touch it again |
| `org` | `string` | `"com.example"` | Reverse domain for the bundle id of the folders fuse adds: `com.example` gives `com.example.<pubspec name>` |
| `solid` | `object` | `{}` | `@solidjs/vite-plugin` option overrides |
| `compile` | `object` | `{}` | Fuse's compile step: `templates: false` turns [templates](/docs/architecture#templates-the-constant-part-is-sent-once) off; `intrinsics` declares wrapper components of other packages (below); `builders` lists value builders whose calls with literal arguments fold into templates (`fuse gen` writes these tables) |
| `gen` | `object` | none | [Generated components](/docs/extending/generating): `libraries` to export (with `allow` / `deny`), `out` directory (default `"fuse"`) |
| `vite` | `object` | `{}` | Vite config overrides |

## How fuse link works

`fuse link` is the glue between npm packages and Dart. Run it from your app directory after installing Fuse packages:

```bash
fuse link
```

It does two things:

### 1. Generates pubspec_overrides.yaml

Adds Dart path dependencies for each Fuse package the app depends on, directly or through another package (`@solid-fuse/adaptive` brings material and cupertino). It follows the dependencies the way Node resolves them, so it works with any package manager's layout:

```yaml title="dart/pubspec_overrides.yaml"
dependency_overrides:
  my_fuse_package:
    path: ../../node_modules/my-fuse-package/dart
```

### 2. Generates fuse_packages.dart

Creates a Dart file that imports each package with an alias and calls its top-level `register` function (whatever name was configured in `fuse.config.ts`):

```dart title="dart/lib/_generated/fuse_packages.dart"
// Generated by fuse link. Do not edit.
import 'package:solid_fuse/solid_fuse.dart' show FuseRuntime;
import 'package:solid_fuse/solid_fuse.dart' as solid_fuse;
import 'package:my_fuse_package/my_fuse_package.dart' as my_fuse_package;

void registerFusePackages(FuseRuntime runtime) {
  solid_fuse.registerSolidFuse(runtime);   // core package
  my_fuse_package.register(runtime);       // your package
}
```

The consumer app just calls `registerFusePackages(runtime)` in `main.dart` and everything is wired up.

## Packages over generated widgets

A package whose components sit on [generated](/docs/extending/generating) widgets (the way `@solid-fuse/material` sits on `material_ui`) ships its TypeScript source instead of a build: the generated modules (`#fuse/material_ui`) belong to the app, so the app compiles the package against them.

- `package.json`: `"exports": { ".": "./src/index.ts" }`, and `src` in `files`.
- `dart/lib/fuse.dart`: what of the Flutter library crosses (`export 'package:material_ui/material_ui.dart';`). Generation reads it in every package the app resolves.
- Import from `#fuse/<package>` in `src/`. For type checking inside the package, point a `paths` entry at an app's generated output.

The app's Vite skips pre-bundling packages that have a `fuse.config`, so their source goes through the app's compile step. A package with only JS (no `dart/`, no `register`) is fine: `@solid-fuse/adaptive` is one. `fuse dev` runs `fuse link` automatically, so consumers don't need to re-run it manually after adding a package.

## Package structure

A typical Fuse package looks like:

```
my-fuse-package/
  src/                    # JS source — wrapper components, factories, exports
    index.ts
    my-widget.tsx
  dart/                   # Dart package
    lib/
      src/
        widgets/          # Widget implementations
        handles/          # Controller and page handle implementations
        register.dart     # register() function
      my_fuse_package.dart  # barrel export (exports register + handles)
    pubspec.yaml
  dist/                   # Built JS output
  fuse.config.ts          # Package config
  package.json
```

## CLI commands

| Command | Description |
|---|---|
| `fuse create [dir]` | Create an app (`--design material\|cupertino\|adaptive\|none`, `--platforms android,ios`, `--org`, `--template <dir or github:owner/repo[/path][#ref]>`, `--no-install`, `--no-git`, `-y`). `bun create solid-fuse` runs the same |
| `fuse dev` | Start Vite dev server + Flutter app with HMR. Links again when a lock file or `pubspec.yaml` changes (`bun add`, `flutter pub add`); press R for the new Dart |
| `fuse build` | Production build (Vite IIFE bundle + Flutter release) |
| `fuse build --js-only` | Build only the JS bundle and skip the Flutter build |
| `fuse link` | Scan packages, generate Dart glue code. Names the app's pub dependencies `dart/lib/fuse.dart` doesn't export |
| `fuse doctor` | Check Flutter, Rust and the Linux tools, and the app's setup, then run `flutter doctor` (`--no-flutter` skips it) |

`fuse build` passes every other argument to `flutter build` (`fuse build apk --release`). With `--js-only` it stops after writing the bundle into the Flutter project's assets — for when only JS changed, or when the bundle ships on its own (for example over the air).
